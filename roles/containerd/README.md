# `containerd` role

The `containerd` role configures [containerd](https://containerd.io/), the container runtime of Kubernetes, on a node:
its configuration file, its proxy settings, the credentials and mirrors of the container registries, and `crictl`.
furyctl runs it during the installation of a cluster and again during an upgrade, when the role also stages the new
containerd version; see the [installer README](../../README.md) for how furyctl uses the roles.

## Requirements

The role expects a node provisioned by furyctl, with:

- the containerd system extension from the
  [installer-immutable-sysext](https://github.com/sighupio/installer-immutable-sysext) repository, with its default
  configuration file generated by Butane;
- the containerd service active when the node starts;
- these directories, with permissions `0755` or stricter: [`containerd_systemd_dir`](#variable-containerd_systemd_dir),
  [`containerd_cfg_dir`](#variable-containerd_cfg_dir), [`containerd_storage_dir`](#variable-containerd_storage_dir) and
  [`containerd_state_dir`](#variable-containerd_state_dir);
- the kernel modules `overlay` and `br_netfilter` loaded;
- the kernel parameters `net.bridge.bridge-nf-call-ip6tables`, `net.bridge.bridge-nf-call-iptables` and
  `net.ipv4.ip_forward` set to `1`.

These requirements were verified with Flatcar Container Linux 4459.2.3 and containerd v2.2.1.

## Proxy

When the variables `http_proxy`, `https_proxy` and `no_proxy` are defined, the role writes them as the `HTTP_PROXY`,
`HTTPS_PROXY` and `NO_PROXY` environment variables of the containerd service, in the systemd drop-in `http-proxy.conf`.
They can also be set for the whole system, as the Flatcar documentation explains in
[System-wide environment variables](https://www.flatcar.org/docs/latest/setup/systemd/environment-variables/#system-wide-environment-variables).

## Role variables

Configure containerd, the container runtime of the node.

Writes the containerd configuration file, a systemd drop-in with the proxy settings of the containerd service and one configuration file per registry of [`containerd_registry_configs`](#variable-containerd_registry_configs), and configures `crictl` to use containerd. When the configuration file, the drop-in or a registry configuration changes, the role restarts containerd and waits until containerd answers `crictl` requests.

During an upgrade, the role stages the new containerd system extension and neither restarts containerd nor reboots the node. The new version and the new configuration take effect when the node reboots: the `os_reboot.yml` entry point of the os-upgrade role reboots it when `os_update_reboot` is `true` and an operating system update or a system extension was staged. When nothing was staged, a configuration change takes effect only at the next restart of containerd.

### `containerd_cfg_dir`<a id="variable-containerd_cfg_dir"></a>

Directory of the containerd configuration. The role writes `config.toml` there, and one `certs.d/<registry>/hosts.toml` file for each registry of [`containerd_registry_configs`](#variable-containerd_registry_configs).

The containerd configuration always tells containerd to read the registry configurations from `/etc/containerd/certs.d`, whatever the value of this variable is.

### `containerd_registry_configs`<a id="variable-containerd_registry_configs"></a>

Registries for which containerd uses credentials, mirrors or no TLS verification. For each entry, the role writes `<containerd_cfg_dir>/certs.d/<registry>/hosts.toml` and adds the credentials to the containerd configuration. The role deletes every directory under `<containerd_cfg_dir>/certs.d` that does not match a registry of the list, including directories that the role did not create.

Each entry is a map with these keys: `registry`, the name of the registry as images refer to it (required); `username` and `password`, the credentials containerd uses for the registry, written only when both are set; `insecure_skip_verify`, `true` to skip the verification of the TLS certificate of the registry; `mirror_endpoint`, a list of URLs of mirrors from which containerd pulls and resolves the images of the registry. For example:

```yaml
- registry: "upstream-registry.example.com"
  username: "admin"
  password: "password"
  insecure_skip_verify: true
  mirror_endpoint:
    - "http://myregistry:8080"
```
